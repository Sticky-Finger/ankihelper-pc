# E2E 自动化测试实现计划（桌面端 integration_test + 产物冒烟）

> **状态：已完成**（2026-09-14，分支 `feature/e2e-testing`）。
> 本地验证全绿：analyze 无问题、44 个单元测试通过、10 个 E2E 用例通过、release 构建 + 冒烟脚本通过。
> 遗留：ci.yml / build.yml 冒烟步骤的远程 Actions 运行待分支 push 后首次验证。
> 与原计划的差异：CI 未做失败截图 artifact（桌面端 `flutter test integration_test` 不自动落盘截图，如需见 `docs/E2E_TESTING.md` 后续扩展）。

> **需求背景**：新功能开发后，希望由 GitHub CI（PR/push 触发）或本地打包后自动执行 E2E 回归，替代一部分人工测试（类似 Selenium 对网页的自动化测试）。
>
> **流程说明**：本任务采用 WORKFLOW.md 步骤 3 的**方式 B · 直接计划流**——AI 生成计划、经用户确认后直接执行，存档于此便于追溯与中断续传。

**目标：** 建立桌面端 E2E 测试体系：`integration_test` 在真实 Windows 窗口中模拟用户操作并断言（主力回归手段），外加 release 产物冒烟脚本（防打包层回归）；接入 GitHub CI。

**技术选型结论（已查证）：**
- ✅ **Flutter 官方 `integration_test`**：官方支持桌面平台在 CI 运行（`flutter test integration_test -d windows`），测试运行在真实桌面窗口（真实渲染/剪贴板/SharedPreferences/HTTP）
- ⚠️ **产物冒烟**：release 构建不暴露 Dart VM 服务，OS 层只能看到顶层窗口（Flutter Windows 仅经 MSAA 桥暴露部分语义树、无 AutomationId），深度黑盒不可行 → 折中为「启动 exe → 断言主窗口出现且存活」
- ❌ 排除：Patrol（不支持桌面）、Appium Flutter Driver（面向移动端且需插桩构建）、pywinauto/FlaUI 深度自动化（元素定位不可靠）

**关键决策（用户确认）：**
1. 形态 = integration_test + 产物冒烟；2. 平台 = 先 Windows；3. CI 触发 = PR + push master（顺带补 PR 测试门禁空缺）；4. 外部依赖 = 全假服务（本地 fake AnkiConnect HTTP 服务 + 词典 Provider override）。

**测试注入点（已核实代码）：**
- `AnkiConnectService({this.baseUrl})` 构造注入 baseUrl（`lib/services/anki_connect_service.dart:19`）→ 本地假服务器零生产代码改动
- `dictionary_provider.dart` 内联 `DictionaryService()` → 需提取为 Provider（唯一小重构）
- `main.dart` 不改，测试自行 `runApp(ProviderScope(overrides: ..., child: AnkiHelperApp()))`

## 风险与备注

- clipboard_watcher 在 CI 交互式会话中的行为待验证，不稳定则跳过该用例
- audioplayers 静态单例不做真实播放断言，只断言 UI 状态变化
- integration_test 默认 debug 模式（JIT）运行，覆盖功能回归足够；性能测试（profile 模式）不在本期范围
- 后续扩展 Linux（`xvfb-run`）/ macOS（直接跑）只需在 ci.yml 加 matrix 项
